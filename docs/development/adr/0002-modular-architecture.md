# ADR-0002 — Четыре модуля: `app`, `core`, `data`, `ui`

- **Статус:** Accepted
- **Дата:** 28.10.2026
- **Связано:** [ARCHITECTURE](../ARCHITECTURE.md) · [RULES §1.2](../RULES.md#12-слои)

## Контекст

Приложение сочетает чистую шахматную логику, хранение прогресса и Compose-UI.
Без границ модулей легко получить:

- `core`, который тянет `android.*` и становится нетестируемым на JVM;
- UI, который напрямую читает Room и знает о схеме БД;
- циклические зависимости и медленную сборку.

При этом проект небольшой: 4 модуля достаточно, чтобы зафиксировать границы,
не превращая сборку в граф из 20 модулей.

## Решение

Четыре модуля:

| Модуль | Ответственность |
| --- | --- |
| `:app` | entry point, DI-контейнер, навигация, locale, platform-адаптеры |
| `:core` | модели, `ChessRules`, `PuzzleSession`, таймер, звёзды, XP, интерфейсы репозиториев |
| `:data` | Room, DataStore, загрузка JSON, реализации репозиториев |
| `:ui` | Compose-тема, компоненты, доска, экраны, ViewModels |

Направление зависимостей:

```text
app → ui → core
app → data → core
core → chesslib
```

`core` не зависит от Android. `ui` не импортирует `data`. `data` не импортирует
`ui`. `app` — единственное место сборки реализаций.

## Последствия

### Положительные

- `core` тестируется на JVM без эмулятора: perft, сессия, таймер, звёзды.
- UI зависит от интерфейсов, а не от Room; экраны легко подменять фейками.
- Границы видны в Gradle и проверяются ревью.
- Сборка быстрее, чем у графа feature-модулей.

### Отрицательные / ограничения

- Нужна дисциплина: соблазн положить `Context` в `core` или DAO в `ui`.
- `:app` знает обо всех модулях; это осознанная точка сборки.
- При росте до 8+ модулей или появлении отдельной фичи (например, онлайн)
  границы придётся пересмотреть — новое ADR.

### Что сделать

- [ ] Создать модули и convention plugins в v0.2.0.
- [ ] Добавить тест-правило, запрещающее `android.*` в `:core` (detekt/forbidden APIs).
- [ ] Проверить, что `:ui` не зависит от `:data` в dependency graph.
- [ ] Зафиксировать правило в PR-чек-листе.

## Альтернативы

| Вариант | Почему нет |
| --- | --- |
| Один модуль `app` | Быстро стартовать, но логика смешивается с Android; тесты медленные |
| Feature-модули (`home`, `puzzle`, `progress`) | Для 4 экранов избыточно; больше Gradle-конфигурации |
| `core` + `app` без `data`/`ui` | Room и Compose протекают в entry point; границы размываются |
| Многомодульный Clean Architecture с use case на каждое действие | Слишком много слоёв для MVP; цена поддержки выше пользы |
