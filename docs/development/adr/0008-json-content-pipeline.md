# ADR-0008 — JSON-паки + машинная валидация в CI

- **Статус:** Accepted
- **Дата:** 28.10.2026
- **Связано:** [CONTENT PLAN](../../design/CONTENT_PLAN.md) ·
  [CONTENT AUTHORING](../CONTENT_AUTHORING.md) ·
  [схема](../../../content/schema/puzzle-pack.schema.json)

## Контекст

Контент — 360 задач с FEN, линией, заданием, рейтингом, темами, тремя
подсказками и разбором на двух языках. Ошибка в FEN или линии ломает задачу и
доверие игрока. Нужен формат, который:

- читается человеком и легко диффится в PR;
- проверяется машиной до сборки;
- не требует сервера и базы данных в приложении;
- переносит прогресс по стабильному ID;
- позволяет добавлять паки без изменения кода.

## Решение

Контент хранится в **JSON-паках** по одному файлу на уровень:

```text
content/puzzles/novice.json
content/puzzles/professional.json
content/puzzles/grandmaster.json
```

Схема — `content/schema/puzzle-pack.schema.json` (JSON Schema 2020-12).
Валидатор — `tools/validate-content.mjs` на Node.js + **chess.js**
(BSD-2-Clause). CI запускает его на каждом PR. В приложении паки лежат в
assets и читаются `kotlinx.serialization`; `contentVersion` показывается в
«О приложении».

Валидатор проверяет:

- схему и обязательные поля;
- легальность FEN и `setupMove`;
- сторону хода после подводки;
- легальность всей линии, нечётную длину, чередование;
- мат в конце для `MATE`;
- `task.plies` = число ходов пользователя;
- дубли ID и FEN;
- локализацию RU/EN;
- диапазон времени и отклонение от формулы;
- источник и лицензию.

## Последствия

### Положительные

- Ошибка ловится до сборки, а не на устройстве.
- Диффы контента читаемы: один объект — одна задача.
- Схема работает в IDE (автодополнение, подсветка ошибок).
- Нет сервера и миграций БД для контента.
- `contentVersion` и стабильные ID сохраняют прогресс.

### Отрицательные / ограничения

- JSON больше, чем бинарный формат; для 360 задач это всё равно < 2 МБ.
- Валидатор не заменяет ручное ревью: альтернативные выигрыши и качество
  объяснения проверяет человек.
- Нужно синхронизировать схему, валидатор и Kotlin-модели.
- Импорт Lichess пока не автоматизирован (KI-008).
- `python-chess` (GPL) не используется; chess.js — BSD-2-Clause.

### Что сделать

- [ ] Подключить валидатор в CI (job `docs-content`).
- [ ] Добавить проверку схемы в IDE (`.vscode/settings.json` — опционально).
- [ ] Сгенерировать Kotlin-модели или держать их вручную в синхроне.
- [ ] Реализовать импорт Lichess и черновики паков.
- [ ] Проверить размер assets после 360 задач.

## Альтернативы

| Вариант | Почему нет |
| --- | --- |
| SQLite/Room с предзаполненной БД | Сложнее диффить и ревьюить; миграции; нет выгоды для 360 задач |
| Remote API | Нужен сервер, сеть, кэш; противоречит офлайн-first |
| Protobuf/FlatBuffers | Меньше размер, но нечитаемо для редактора и сложнее пайплайн |
| YAML | Удобнее для людей, но больше парсеров/неоднозначностей; JSON уже есть в Kotlin |
| Хранить контент в коде Kotlin | Пересборка на каждую задачу, нет схемы и CI-валидации |
